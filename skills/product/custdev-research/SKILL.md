# CustDev Research — записи интервью → карточка исследования

Навык превращает одну или несколько записей исследования в готовый артефакт: стенограмму с
атрибуцией реплик, профили респондентов, список продуктовых болей с привязкой к говорящему,
фоллоуап, DOCX и строку в реестре.

## Когда использовать

- у тебя есть запись кастдев-интервью или UX-тестирования (`.webm`, `.mp3`, `.m4a`, видео с
  записью экрана) и нужен разбор, а не просто расшифровка;
- запись разбита на части (созвон разорвался, две сессии подряд) — части склеиваются в одну встречу;
- интервью уже расшифровано в текст/JSON и нужна разметка спикеров и инсайты;
- сессия групповая: ведущий + 2–4 респондента, реплики нужно разнести по людям.

## Когда НЕ использовать

| Задача | Правильный навык |
| :--- | :--- |
| Обычная рабочая встреча, нужен протокол/фоллоуап | `meeting-transcriber` |
| Спроектировать исследование, гайд интервью | `hypothesis-designer`, `next-move-theory`, `AJTBD` |
| Только расшифровка без разбора | `meeting-transcriber` |

## Быстрый старт

```bash
pip install -r requirements.txt     # groq, python-dotenv, python-docx (+ системный ffmpeg)

# 1) интервью 1-на-1
python3 skills/product/custdev-research/scripts/process_custdev.py \
  --audio "Meets/audio/Алиса.webm" \
  --interviewer "Влад JGGL" --respondent "Алиса" \
  --title "Кастдев и UX-тестирование JGGL — Алиса" \
  --output-docx "Meets/Стенограмма_и_Фоллоуап_Алиса.docx"

# 2) групповая сессия из двух частей
python3 skills/product/custdev-research/scripts/process_group_custdev.py \
  --files "part1.webm" "part2.webm" \
  --interviewer "Интервьюер (JGGL)" \
  --respondents "Глеб" "Камиль" "Стас" \
  --hint "Глеб: 27 лет, нейродизайнер" --hint "Камиль: 24 года, архитектор-дизайнер" \
  --title "Групповой кастдев — 12.11.2026" --slug "группа_12.11" \
  --output-docx "Meets/Стенограмма_и_Фоллоуап_Группа.docx"

# 3) уже готовая расшифровка (текст с таймкодами)
python3 skills/product/custdev-research/scripts/process_text_custdev.py \
  --input transcript.txt --interviewer "Влад JGGL" --respondent "Алекс"
```

Скрипты работают из корня проекта пользователя: `BASE_DIR` определяется по `--`/env
`CUSTDEV_BASE_DIR`, иначе поиском вверх от текущей папки по признакам `Meets/` или `.git`.

## Пайплайн

1. **Аудио → текст.** `transcribe_groq.py`: ffmpeg нарезает файл на чанки по 10 минут (лимит
   Groq 24 МБ), модель `whisper-large-v3` с фолбэком на `whisper-large-v3-turbo`, таймкоды
   склеиваются со смещением.
2. **Текст → спикеры.** `llm_diarizer.py`: семантическая диаризация (см. ниже).
3. **Спикеры → профиль и боли.** `custdev_analyzer.py`: профиль респондента + нумерованные
   продуктовые наблюдения, каждый пункт с меткой говорящего `[Имя]`.
4. **Сборка.** Единый фоллоуап (дедуп пунктов между частями), DOCX через `docx_generator.py`,
   строка в реестре.
5. **Кэш.** Готовые части и извлечённые инсайты складываются в тот же JSON — повторный прогон
   встречи не тратит токенов.

## Диаризация (v2)

Классические акустические диаризаторы путаются на записях с наушников и моно-дорожках, поэтому
спикеры размечаются **по смыслу реплик** LLM-моделью:

| Механика | Как работает |
| :--- | :--- |
| Окна | не по числу сегментов, а по **токен-бюджету** (~4000 токенов prompt ≈ 100–150 сегментов) |
| Перехлёст | 8 предыдущих сегментов идут как контекст и не оплачиваются второй раз |
| Ответ | прогоны `{"runs": [["Глеб", 3], ["Интервьюер", 1]]}` — в групповой сессии ~55 записей вместо 303 |
| Валидация | сумма прогонов обязана совпасть с числом сегментов: иначе по-индексный повтор → деление окна пополам → авто-метка |
| Маркеры | `⇄` (перебивание) и `⏸` (пауза ≥ 1 с) вместо пары таймкодов |
| Пол | сильнейший сигнал в русском: «я хотел/хотела» согласуется с родом говорящего |

Экономия против окон по 30 сегментов: **−50…−60% токенов** на встречу.

```bash
DIARIZER_TOKEN_BUDGET=4000   # больше окно — меньше вызовов, но упирается в TPM модели
DIARIZER_OVERLAP=8           # сколько сегментов предыдущего окна давать как контекст
DIARIZER_MAX_RUN=20          # прогон длиннее — считать подозрительным (только с VERIFY_RUNS)
DIARIZER_VERIFY_RUNS=1       # перепроверять длинные прогоны по индексам (дороже, точнее)
```

## Ключи, лимиты и бюджет

Groq считает лимиты **на аккаунт и на модель**: `openai/gpt-oss-120b` — 8 000 токенов/мин,
200 000 токенов/сутки; whisper — секунды аудио в сутки. Один ключ выгорает за 6–8 встреч,
поэтому все вызовы идут через кольцо ключей `scripts/groq_keys.py`.

```bash
# ключи: любой из способов, порядок = приоритет
GROQ_API_KEYS="gsk_ключ1,gsk_ключ2"     # .env
# или файл groq_keys.txt в корне проекта (по ключу на строку)
# или ~/.groq_keys

python3 scripts/groq_keys.py status   # состояние ключей и остаток бюджета
python3 scripts/groq_keys.py check    # живой 1-токенный прогон по каждому ключу
python3 scripts/groq_keys.py usage 30 # расход за 30 суток по локальному логу
python3 scripts/groq_keys.py reset    # забыть состояние (например, на следующий день)
```

Что делает кольцо:

- `429 tokens per day` → ключ помечается выгоревшим с ETA сброса, запрос уходит на следующий;
- `429 per minute` → ротация или короткое ожидание;
- `401/403` → ключ отключается навсегда;
- `413 Request too large` → не меняет ключ и модель, а дробит окно;
- **учёт расхода** по (ключ, модель, UTC-день): токены in+out и секунды аудио, лог в
  `.cache/groq_usage.jsonl`, состояние в `.cache/groq_keys_state.json`;
- **pre-flight**: в начале пайплайна печатается остаток и вердикт «влезает / не влезает»;
- лимиты, которые API не отдаёт в заголовках (дневные), выучиваются из текста 429
  (`Limit 200000, Used 198589`) и дальше проверяются до отправки запроса.

⚠️ API **не отдаёт остаток дневного бюджета** — только минутный. Всё дневное считается локально,
поэтому правда о расходе — либо в консоли Groq (`console.groq.com/usage`), либо в `usage`-логе.

⚠️ Ротация ключей ради обхода лимитов нарушает ToS Groq. Кольцо рассчитано на ключи, которые
принадлежат тебе легально (свой аккаунт, командные аккаунты, Dev-tier).

## Артефакты и реестр

```
<BASE_DIR>/Meets/transcripts/<slug>.json        стенограмма: timeline[{start,end,text,speaker}] + diarization
<BASE_DIR>/Meets/followups/<slug>.txt            фоллоуап (профили + нумерованные боли)
<BASE_DIR>/Meets/Стенограмма_и_Фоллоуап_*.docx    брендированный документ
<BASE_DIR>/Meets/реестр_кастдевов.md             строка реестра на каждый прогон
```

Переопределяется через env: `CUSTDEV_BASE_DIR` (корень проекта), `CUSTDEV_REGISTRY`
(путь к реестру). Формат реестра и пример строки — `references/registry-format.md`.

## Validation gates

Перед тем как отдавать результат:

1. **Полнота разметки** — в JSON нет `null`-спикеров, сумма по спикерам равна числу сегментов.
2. **Осмысленность распределения** — ведущий не может иметь 3 реплики из 300, а один
   респондент — 90% (признак склейки прогонов). Лечится `DIARIZER_VERIFY_RUNS=1` и повторным
   прогоном с `--force`.
3. **Профили не пустые** — на каждого респондента есть возраст/роль/опыт в AI; если модель не
   смогла, передай факты вручную через `--hint` / `--profile`.
4. **Пункты болей привязаны к людям** — каждый имеет метку `[Имя]`, гипотезы ведущего в список
   не попадают.
5. **Реестр дополнен** — в конце файла появилась строка с датой, ссылками и статусом.
6. **Секреты** — `.env` и `groq_keys.txt` не в git (проверь `git status`).

## Troubleshooting

| Симптом | Причина / что делать |
| :--- | :--- |
| `all Groq keys exhausted … (nearest reset in 1h02m)` | дневной лимит всех ключей; ждать, добавить ключ или `usage`/`status` чтобы увидеть расклад |
| `Request too large for model qwen/...` | окно больше TPM этой модели — уменьши `DIARIZER_TOKEN_BUDGET` (авто-дробление уже встроено) |
| Фолбэк ушёл на `qwen` и разметка стала мусором | слабая модель на шумной ASR; нужен `gpt-oss-120b`, то есть живой дневной бюджет ключа |
| `⚠️ Source media not found … using saved transcription` | аудио перемещено, но `--raw-json` цел — пайплайн продолжит на сохранённой расшифровке |
| Повторный прогон ничего не делает | сработал кэш; пересчитать заново — `--force` |
| DOCX пустой / без стилей | не установлен `python-docx`, либо не передан `--output-docx` |
