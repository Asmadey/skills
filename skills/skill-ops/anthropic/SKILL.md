# Authoring Skills
 
Основа: Anthropic «Skill authoring best practices» (platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) + практические выводы о том, как модели реально читают скиллы.
 
Ключевой сдвиг: качество скилла сегодня больше определяется **структурой файлов и встроенными проверками**, чем красотой формулировок. Современные модели умны — добавляй только то, чего модель не знает.

## Выбор режима
 
- Пользователь хочет новый скилл → **Режим A**.
- Пользователь даёт существующий скилл / папку `.claude/skills` / просит «проверь», «прокачай», «аудит» → **Режим B**.
## Режим A: создание скилла
 
Скопируй чек-лист в ответ и отмечай по ходу:
 
```
Skill Build:
- [ ] 1. Понять задачу: что делает скилл, когда срабатывает, 2–3 реальных примера запроса
- [ ] 2. Найти пробелы: что модель делает плохо БЕЗ скилла (baseline)
- [ ] 3. Разметить шаги по степени свободы (high / medium / low)
- [ ] 4. Спроектировать структуру файлов (SKILL.md + references + scripts)
- [ ] 5. Написать frontmatter и минимальное тело
- [ ] 6. Добавить чек-лист (если порядок важен) и цикл самопроверки (если качество критично)
- [ ] 7. Прописать зависимости рядом с каждым скриптом
- [ ] 8. Составить 3 eval-сценария и прогнать
- [ ] 9. Прогнать финальную проверку (раздел ниже); при провале — вернуться к шагу 5
```
 
**Шаг 2.** Минимальные инструкции, закрывающие реальные пробелы, лучше исчерпывающих. Не объясняй то, что модель и так знает (что такое PDF, как работает pip).
 
**Шаг 3.** Для каждого шага задай вопрос: «Что случится, если модель сделает это по-другому?» Ничего страшного → high freedom. Есть последствия (деньги, удаление, миграции, отправка наружу) → low freedom, лучше скрипт.
 
**Шаг 8.** Формат eval:
 
```json
{
  "skills": ["skill-name"],
  "query": "реальный запрос пользователя",
  "files": ["test-files/input.ext"],
  "expected_behavior": ["наблюдаемый результат 1", "результат 2", "результат 3"]
}
```
 
## Режим B: аудит существующего скилла
 
Важно: **сначала показать отчёт и предлагаемые изменения, менять файлы — только после подтверждения пользователя.**
 
```
Skill Audit:
- [ ] 1. Инвентаризация: дерево файлов, длина каждого файла
- [ ] 2. Проверка по правилам 1–9 (см. ниже)
- [ ] 3. Проверка frontmatter и анти-паттернов
- [ ] 4. Отчёт: таблица «правило → статус (OK / FIX / N/A) → что изменить»
- [ ] 5. Получить подтверждение пользователя
- [ ] 6. Внести правки
- [ ] 7. Перепроверить по пунктам 1–3; если что-то не прошло — вернуться к шагу 6
```
 
**Шаг 1 — запусти как есть** (low freedom, только чтение):
 
```bash
SKILL_DIR="путь/к/скиллу"
# длина всех файлов
find "$SKILL_DIR" -type f \( -name '*.md' -o -name '*.py' -o -name '*.js' -o -name '*.sh' \) -exec wc -l {} + | sort -n
# reference-файлы >100 строк без оглавления в первых 30 строках
for f in $(find "$SKILL_DIR" -name '*.md' ! -name 'SKILL.md'); do
  n=$(wc -l < "$f")
  if [ "$n" -gt 100 ] && ! head -30 "$f" | grep -qiE '^#+ *(contents|оглавление|содержание)'; then echo "NO TOC ($n lines): $f"; fi
done
# ссылки из каждого .md на другие .md (для поиска вложенности)
grep -oHE '\]\([^)]+\.md\)' -r "$SKILL_DIR" --include='*.md'
# Windows-пути
grep -rnE '[a-zA-Z0-9_]\\[a-zA-Z0-9_]+\.(py|md|js|sh)' "$SKILL_DIR" || true
```
 
Формат отчёта:
 
| # | Правило | Статус | Находка | Предлагаемое изменение |
|---|---------|--------|---------|------------------------|
 
В конце — топ-3 изменения по влиянию на результат.
 
## Правила 1–9 (ядро)
 
### 1. Оглавление в длинных reference-файлах
При открытии длинного файла модель часто делает `head -100`, чтобы решить, нужен ли он. Всё, что ниже 100-й строки, для неё может «не существовать».
**Правило:** любой reference-файл >100 строк начинается с `## Contents`, совпадающего с заголовками файла.
 
```markdown
# API Reference
 
## Contents
- Authentication and setup
- Core methods (create, read, update, delete)
- Error handling patterns
- Code examples
 
## Authentication and setup
...
```
 
### 2. Степени свободы под хрупкость шага
 
| Уровень | Форма | Когда | Пример |
|---|---|---|---|
| High | Текстовые цели | Много верных подходов, решение зависит от контекста | Код-ревью, разбор звонка продаж, пост в Telegram/LinkedIn |
| Medium | Шаблон/псевдокод с параметрами | Есть предпочтительная форма, вариации допустимы | Еженедельный отчёт клиенту (`format`, `include_charts`) |
| Low | Конкретный скрипт, 0–мало параметров | Хрупко, нужна строгая последовательность | Миграция БД, выставление счёта, удаление пользователей |
 
- Один скилл может **смешивать уровни**: «написать текст письма» — high, «создать инвойс» — low.
- Low freedom = **скрипт, а не больше текста**. Скрипт работает одинаково на любой модели, а его код не тратит контекст (выполняется, а не читается).
- Для low: «Run exactly this. Do not modify the command or add flags.»
### 3. Тестирование на каждой целевой модели
Результат скилла зависит от модели. Вопрос на каждую:
- **Haiku:** хватает ли ему инструкций?
- **Sonnet:** ясно ли и эффективно?
- **Opus / новые reasoning-модели:** не переобъясняет ли скилл?
Практика: прогнать один и тот же запрос на всех целевых моделях.
- Маленькая модель пропустила шаг → сделать шаг яснее или превратить в скрипт.
- Сильная модель со скиллом хуже, чем без него → **вырезать** инструкции (старые КАПСЫ, «IMPORTANT», избыточные нумерованные микрошаги), пока не станет лучше.
В тело скилла добавить строку совместимости (особенно если скилл будут шарить):
 
```markdown
## Model compatibility
Tested on: Opus, Sonnet. Haiku: шаг 3 нестабилен — используй scripts/x.py.
```
 
### 4. SKILL.md < 500 строк, это оглавление
SKILL.md — навигатор: быстрый старт + ссылки на детали. При приближении к лимиту — выносить в отдельные файлы.
Дробить reference **по доменам**: `reference/finance.md`, `reference/sales.md`… (или по клиенту для клиентских отчётов) — вопрос про выручку не грузит marketing.md.
 
### 5. Ссылки строго на один уровень
Плохо: `SKILL.md → advanced.md → details.md` — нижний файл, скорее всего, будет прочитан частично.
Хорошо: каждый reference-файл линкуется **прямо из SKILL.md**. При аудите: список всех файлов, на которые ссылается SKILL.md; любой файл, достижимый только через другой файл, — перелинковать напрямую.
 
### 6. Чек-лист для многошаговых процессов
Если **порядок важен** (проверить данные → потом строить отчёт), дай чек-лист, который модель копирует в ответ и отмечает. Если порядок не важен — чек-лист не нужен, дай цель.
Пункты — цели, а не микроинструкции. Под каждым — короткий абзац. Последний пункт — проверка с возвратом: «If citations are incomplete, return to Step 3» — это не даёт отметить проваленный шаг.
 
### 7. Цикл самопроверки (feedback loop)
Паттерн: **проверить → исправить → повторить, пока не пройдёт.** Проверка не обязана быть кодом — это может быть style guide / brand voice.
 
```markdown
1. Draft following STYLE_GUIDE.md
2. Review against the guide; note each issue with the section it breaks
3. Revise, review again
4. Finalize only when all checks pass
```
 
Самоулучшение: если черновик провалился по причине, которой ещё нет в гайде, — в конце прогона **предложить новое правило**; после одобрения пользователем оно добавляется в гайд.
 
### 8. Зависимости явно, рядом со скриптом
Не предполагать, что инструмент установлен. Плохо: «Use the PDF library». Хорошо:
 
```markdown
Install: `pip install pypdf` (skip if already installed)
```
 
У каждого скрипта — строка установки рядом. Учесть платформу: в claude.ai/Cowork можно ставить из PyPI/npm; в Claude API сети нет — зависимости должны быть предустановлены.
 
### 9. Портативность
Скилл должен работать на чужой машине в первый день: никаких абсолютных путей вашего ноутбука, только относительные и прямые слэши (`scripts/helper.py`); MCP-инструменты — полным именем `ServerName:tool_name`.
 
## Frontmatter и description
 
- `name`: ≤64 символов, `a-z0-9-`, без XML, без слов `anthropic`/`claude`. Предпочтительно герундий: `processing-pdfs`, `analyzing-spreadsheets`. Избегать `helper`, `utils`, `documents`.
- `description`: непустой, ≤1024 символов, без XML, **в третьем лице** («Extracts…», не «I can…» / «You can…»). Обязательно **что делает + когда использовать** + ключевые слова-триггеры (включая русские, если пользователь пишет по-русски).
  - Хорошо: «Extracts text and tables from PDF files, fills forms, and merges documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.»
  - Плохо: «Helps with documents».
## Структура папки
 
```
skill-name/
├── SKILL.md          # навигатор, <500 строк
├── reference/        # по доменам; >100 строк → Contents сверху
│   ├── finance.md
│   └── sales.md
├── examples.md
└── scripts/          # low freedom; исполняются, не читаются
    └── validate.py
```
 
Имена файлов описательные (`form_validation_rules.md`, не `doc2.md`). В тексте явно указывать намерение: «Run `analyze.py`» (выполнить) vs «See `analyze.py` for the algorithm» (прочитать).
 
## Паттерны контента
 
- **Template:** строгий («ALWAYS use this exact structure») или гибкий («sensible default, adapt as needed») — выбирать по степени свободы.
- **Examples:** 2–3 пары input → output для задач, где важен стиль.
- **Conditional workflow:** «Создаёшь новое? → workflow A. Редактируешь? → workflow B».
- **Plan-validate-execute** для пакетных/деструктивных операций: план в файл (`changes.json`) → валидация скриптом → выполнение → проверка результата.
- Консистентная терминология: один термин на понятие на весь скилл.
- Без датозависимых формулировок; устаревшее — в секцию «Old patterns» под `<details>`.
## Скрипты
 
- Решать ошибки в скрипте, а не перекладывать на модель (обработать FileNotFound, PermissionError).
- Никаких «магических чисел» — каждая константа с комментарием «почему».
- Валидаторы — с подробными сообщениями: «Field 'signature_date' not found. Available: customer_name, order_total».
## Анти-паттерны
 
- Переобъяснение того, что модель знает.
- Много вариантов без дефолта («можно pypdf, или pdfplumber, или…») → дать один дефолт + escape hatch.
- Вложенные ссылки глубже одного уровня.
- Длинный reference без оглавления.
- Windows-пути `scripts\helper.py`.
- Избыточная эмфаза (MUST, IMPORTANT, CAPS) под старые модели — для новых ухудшает результат.
- Неуказанные зависимости.
## Финальная проверка
 
Прогнать перед сдачей; любой пункт «нет» → исправить и прогнать снова.
 
**Core**
- [ ] description конкретный, 3-е лицо, «что + когда», ключевые триггеры
- [ ] SKILL.md < 500 строк, детали вынесены
- [ ] reference-файлы >100 строк имеют Contents
- [ ] все ссылки на один уровень от SKILL.md
- [ ] степень свободы соответствует хрупкости каждого шага
- [ ] чек-лист там, где важен порядок; с шагом возврата
- [ ] цикл самопроверки для качественно-критичных задач
- [ ] терминология консистентна, примеры конкретны, нет датозависимого текста
**Code**
- [ ] скрипты обрабатывают ошибки сами
- [ ] нет магических чисел
- [ ] установка зависимостей рядом с каждым скриптом
- [ ] только прямые слэши; MCP-инструменты с префиксом сервера
**Testing**
- [ ] ≥3 eval-сценария
- [ ] прогнано на всех целевых моделях; совместимость записана в скилле
- [ ] проверено на реальных запросах
