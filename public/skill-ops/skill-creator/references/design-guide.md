# Архитектурное руководство по разработке навыков (Design Guide)

Данное руководство содержит фундаментальные принципы, стандарты спецификации (agentskills.io) и практические рекомендации для создания высокоэффективных навыков ИИ-агентов.

---

## 1. Концепция Progressive Disclosure (Уровни L1 / L2 / L3)

Экономия контекста — главный приоритет при разработке навыков. Навык загружается поэтапно по мере необходимости:

```
[Level 1: Discovery] (~100 токенов)
├── Загружается на старте сессии в системный промпт
└── Содержит только name и description из frontmatter
          │
          ▼ (При совпадении с запросом пользователя)
[Level 2: Activation] (< 5000 токенов)
├── Читается тело файла SKILL.md
└── Содержит обзор, сценарии вызова, ключевой воркфлоу, форматы вывода
          │
          ▼ (По мере исполнения сложных задач)
[Level 3: Execution] (Без практического лимита)
├── scripts/    — исполняются без обязательной загрузки исходного кода в контекст
├── references/ — узкоспециализированные справки (API, краевые случаи, стандарты)
├── resources/  — пакеты глубоких знаний, правила предметной области
└── assets/     — шаблоны документов, шрифты, заготовки для генерации
```

> **Правило:** Базовый `SKILL.md` должен быть компактным. Все детали, которые требуются лишь в 20% случаев, выносите в `references/` на уровень L3. Ссылки должны быть прямыми (глубиной в 1 уровень: `SKILL.md` → `references/doc.md`), без многоуровневых цепочек.

## 2. Две философии дизайна навыков

Любой навык относится к одному из двух фундаментальных паттернов:

### Паттерн A: Capability Primitives (Инструментальные обертки)
* **Назначение:** Добавляет новую техническую способность (доступ к API, работу с нестандартным форматом файлов, браузер, парсер).
* **Источник надежности:** Детерминированный программный код (CLI, Python/Bash скрипты), а не промпты.
* **Объем `SKILL.md`:** 30–80 строк, состоящих преимущественно из примеров команд и флагов.
* **Принцип:** «Детерминизм выноси в код; суждения оставляй промптам».

### Паттерн B: Process Primitives (Когнитивные дисциплины и методологии)
* **Назначение:** Задает структурированный алгоритм мышления (TDD, код-ревью, аудит архитектуры, дизайн-выравнивание).
* **Источник надежности:** Четкий пошаговый процесс, контрольные списки (checklists) и циклы верификации.
* **Объем `SKILL.md`:** Структурированный текст без обязательного наличия исполняемых скриптов.
* **Принцип:** Ограничивает хаос рассуждений LLM жесткими рамками протокола.

## 3. Инженерия описания (Description as Routing Contract)

Поле `description` во frontmatter — **единственное**, что видит агент до принятия решения об активации навыка. Если навык не вызывается вовремя, в 95% случаев проблема в `description`.

### Формула идеального описания
Включайте ровно три элемента:
1. **Что** делает навык (краткая функция).
2. **Когда** его использовать (триггерные фразы и контекстные ситуации).
3. **Отличие (Differentiator)** от смежных навыков (предотвращает конфликты маршрутизации).

```yaml
# Шаблон:
description: "[Что делает]. Используйте, когда [триггеры, ситуации, фразы пользователя]. Отличие: [почему именно этот навык, а не альтернативы]."
```

### Критические правила описания:
- **Никогда не описывайте полный пошаговый процесс в `description`.** Если в описании есть шаги *как* это делать, агент выполнит их сразу по памяти и не станет загружать тело `SKILL.md`. Описание отвечает на вопрос *«Стоит ли открывать этот навык?»*, а не *«Каковы шаги?»*.
- **Опасность двоеточия:** Строгие парсеры YAML (например, в Codex/Pi) падают с ошибкой при наличии `: ` (двоеточие с пробелом) внутри неэкранированного значения. Если внутри описания нужно двоеточие, оборачивайте значение в двойные кавычки: `description: "..."`.
- **Запрет угловых скобок:** Не используйте `<` и `>` в описании (они могут вызвать инъекции в системный промпт агента).

## 4. Градации жесткости инструкций (Degrees of Freedom)

Подбирайте уровень жесткости формулировок в зависимости от критичности ошибки:

1. **Эвристики (Heuristics / Высокая свобода):**
   * Для задач, где допустимо множество решений (код-ревью, стилистика, выбор библиотеки).
   * Формат: списки рекомендаций, буллеты, общие принципы.
2. **Шаблоны (Templates / Средняя свобода):**
   * Когда есть предпочтительная структура, но адаптация приветствуется (формат отчета, структура коммита).
   * Формат: примеры Markdown-разметки или псевдокод.
3. **Скрипты и жесткие правила (Scripts / Нулевая свобода):**
   * Для хрупких, многошаговых и критических операций (миграции БД, патчинг файлов, деплой).
   * Формат: детерминированные bash/python скрипты с явной инструкцией «запусти скрипт, не пытайся повторять логику вручную».

## 5. Циклы верификации (Validation Loops)

Любой надежный процесс должен содержать явный цикл: **Действие $\rightarrow$ Верификация $\rightarrow$ Исправление $\rightarrow$ Повторная проверка**.

* **Для документов:** Визуальный QA-прогон перед финальной сдачей.
* **Для кода:** Запуск тестов + отсутствие ошибок типов (`tsc`, `mypy`) перед коммитом.
* **Для навыков:** Запуск `quick_validate.py` перед релизом.
* **Для данных:** Проверка по JSON/Zod схеме перед передачей дальше.

## 6. Каталог анти-паттернов (Чего делать НЕЛЬЗЯ)

1. ❌ **Не переобучайте модель тому, что она уже знает.** Не пишите туториалы по синтаксису Python, объяснения «что такое git» или основы HTTP. Добавляйте только специфичный контекст проекта.
2. ❌ **Никакой пользовательской документации внутри папки навыка.** Внутри папки навыка не должно быть файлов `README.md`, `CHANGELOG.md` или `INSTALL.md`. Навыки предназначены для агентов, а не для людей.
3. ❌ **Избегайте размытых описаний.** Описания вроде *«Полезный навык для работы с кодом»* гарантируют ложные срабатывания либо полное игнорирование.
4. ❌ **Не создавайте монолитные мега-навыки.** Если один навык объединяет дизайн, бекенд, маркетинг, деплой и тестирование — разбейте его. Навыки должны комбинироваться во время выполнения задачи.
5. ❌ **Не надейтесь, что агент догадается сам.** Описывайте критические шаги явно. Вместо *«Затем задеплойте»* пишите *«Запустите `npm run deploy` и дождитесь HTTP 200 на эндпоинте /healthz»*.
6. ❌ **Не используйте абсолютные пути.** Всегда используйте относительные пути с прямыми слэшами (`/`), независимые от операционной системы.
7. ❌ **Не вшивайте устаревающую информацию.** Сведения вроде *«По состоянию на 2024 год...»* быстро устаревают. Динамические данные получайте через скрипты или веб-поиск.

## 7. Аудит безопасности сторонних навыков

Перед установкой или импортом стороннего навыка выполните аудит:
- [ ] Изучите все файлы в директории `scripts/` на предмет несанкционированных сетевых запросов или попыток чтения приватных файлов (`.env`, `~/.ssh`).
- [ ] Проверьте файлы в `references/` на наличие скрытых prompt injection (например, *«Ignore previous instructions...»*).
- [ ] Убедитесь, что имя навыка не имитирует известные системные навыки (защита от typosquatting).

---

## 8. Чек-лист готовности к релизу (Ship Checklist)

Перед завершением создания или редактирования навыка проверьте:

- [ ] **Имя:** Поле `name` во frontmatter строго в `kebab-case` (1–64 символа) и точно совпадает с именем директории.
- [ ] **Описание:** Содержит Что + Когда + Отличие.
- [ ] **Триггеры:** Описаны вероятные пользовательские фразы и явные Negative Triggers.
- [ ] **Синтаксис YAML:** Описание экранировано кавычками при наличии `: `, отсутствуют угловые скобки `<>`.
- [ ] **Файлы:** Отсутствуют человеческие `README.md` / `CHANGELOG.md` внутри папки навыка.
- [ ] **Пути:** Использованы только относительные пути.
- [ ] **Цикл верификации:** В воркфлоу описан шаг проверки результатов.
- [ ] **Автоматизация:** Запущен и успешно пройден скрипт `quick_validate.py`.
